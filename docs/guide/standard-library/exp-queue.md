# `gpp/exp/queue`

`gpp/exp/queue` is an experimental, single-process work queue with local disk
durability. It stores messages in the `./app.queue` file by default (in the
current directory), then executes them in the background. Use a different file
path when you need a separate queue.
Do not open the same queue file from multiple processes or queue instances.

## Define and push messages

Derive message classes from `queue.Message` and implement the protected
`_execute() error` hook. The queue calls it when the message is ready to run.

`Priority` defaults to `0`; larger values run first, and messages at equal
priority run in insertion order:

```gpp
import (
    "fmt"
    "time"
    queue "gpp/exp/queue"
)

class EmailMessage : queue.Message {
    Recipient string
    Subject string

    func _execute() error {
        fmt.Println("sending", this.Subject, "to", this.Recipient)
        return nil
    }
}

class BuildReportMessage : queue.Message {
    Build string

    func _execute() error {
        fmt.Println("publishing build report", this.Build)
        return nil
    }
}

q := queue.New()
q.Push(BuildReportMessage(Priority: 10, Build: "v2.4.0"))
q.Push(EmailMessage(Priority: 1, Recipient: "dev@example.com", Subject: "Build complete"))
q.Drain(30 * time.Second)
```

## Control execution

During `_execute()`, `this.ExecutionContext()` gives the message control over
what the queue does after the current call returns. Call the methods below on
that context:

- `Signal()` returns the signal that woke this message, if it was waiting.
- `Continue()` asks the queue to checkpoint the message and run it again after
  `_execute()` succeeds. Update the message fields first to record progress.
- `WaitFor(signal, timeout, timeoutEvent)` asks the queue to checkpoint and
  pause the message until the signal arrives or the timeout event is delivered.
- `RetryLimit(n)` overrides the queue's default retry count if this execution
  fails.

These controls do not interrupt or cancel a running `_execute()`. Ordinary
one-shot messages can ignore the execution context.

`New` starts the worker automatically. `Push` serializes and syncs each message
before returning. Message serialization is generated by GPP because
`queue.Message` is serializable and subclasses inherit that metadata.

`retries` counts additional attempts after the first; its default is `3`.
When all attempts fail, the message is kept in the durable dead-letter set.
`q.Dead()` returns entries with the original concrete message in `Message`,
plus its retry count and last error. Fetching entries does not remove them.
Pass an entry to `q.Remove(entry)` to remove one, or call `q.Purge()` to clear
all dead-letter entries.

On startup, the queue replays its log and compacts completed-message history;
the size threshold also triggers compaction when it is exceeded.

## Shutdown

`Drain(timeout)` stops accepting new messages and waits for queued work to
finish. If it times out, it returns an error and signals the worker to stop
after its current message execution; cleanup may finish after `Drain` returns, and
unprocessed messages remain durable for the next run. `Stop()` stops after the
current message execution and waits for shutdown to finish, leaving pending
messages in the queue file.

For checkpointed sequential work, `gpp/exp/workflow` builds on this same queue
and stores progress in the same queue file. See the [workflow guide](./exp-workflow).

Failed message executions are retried, so `Drain` can time out if a message keeps
failing. Delivery is at least once; make `_execute` safe to run again if the
process stops before an acknowledgement is recorded. The queue is not shared
between processes; use one open queue instance per file.

See the [queue specification](/reference/specifications/std.exp.queue) for log
format, recovery, and API details.
