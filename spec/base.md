Project: Go++ v0.2 — a Go-like language that transpiles to ordinary Go

Core goal
- Preserve Go’s runtime model, stdlib access, tooling, deployment simplicity, goroutines, channels, and generated Go interoperability.
- Improve syntax/ergonomics without turning the language into C++, Rust, or framework-heavy C#.
- Source-to-source compiler first: .gpp -> generated .go -> go build.
- Compiler implemented in Go.
- Handwritten parser is acceptable/preferred initially; PEG tooling is optional, not required.

Packages
- One package declaration maximum per source file.
- No package declaration defaults to package main.
- Source directory structure does not determine package.
- Dotted package names are supported:
    package telga.web
    package telga.db.models
- Dotted packages are logical namespaces in Go++.
- The transpiler maps them onto generated Go directory paths:
    telga.web -> telga/web
    telga.db.models -> telga/db/models
- The final segment becomes the emitted Go package identifier.
- Files from different logical packages may live side-by-side in the source tree.
- The generated Go module path is configurable and is used for local package
  imports; the CLI defaults it to `generated`.


Imports
- Use Go's quoted import syntax unchanged for standard-library and external
  Go packages, including single imports, grouped imports, aliases, dot imports,
  and blank imports:
    import "fmt"
    import (
        "net/http"
        j "encoding/json"
    )
- Import local Go++ packages by their logical dotted name, such as
  `import telga.web`; the compiler maps that name to the configured generated
  Go module path. Generated output paths are compiler internals and cannot be
  imported directly from Go++ source.
- Preserve seamless access to the Go standard library and normal Go packages.

Classes
- Add:
    class Person {
        Name string
        Age int

        func Greet() string {
            ...
        }
    }
- Classes transpile to Go structs.
- Methods declared inside classes transpile to Go receiver methods.
- Implicit receiver name:
    this
- Within an instance method, an unqualified class field reference is resolved
  against the receiver and lowered as `this.Field`; explicit `this.Field` is
  also valid.
- An unqualified call to another instance method resolves against the same
  receiver. Static methods and top-level functions do not have an implicit
  instance receiver.
- Parameters and local variables shadow class members with the same name.
- Example:
    func Greet() string
  becomes:
    func (this *Person) Greet() string
  and a body reference to `Name` becomes `this.Name` when no local or parameter
  named `Name` is in scope.

Inheritance
- Support inheritance syntax:
    class Employee : Person {
        ...
    }
- Multiple inheritance is desired:
    class C : A, B {
        ...
    }
- Initial implementation may map inheritance to Go struct embedding.
- If members clash across parents, do not silently pick a winner; require qualified access for ambiguity.
- Eventually support true polymorphic dispatch rather than Go embedding alone.
- Hidden vtable/dispatch machinery may be generated by the compiler.
- This implementation detail must remain invisible to normal Go++ code.
- Everything should behave polymorphically by default; no explicit override keyword.

Construction / initialization
- Keep normal Go-style literals available.
- Add compact constructor-style initialization:
    p := Person("Bob", 42)
- Also consider named constructor-style initialization:
    p := Person(
        Name: "Bob",
        Age: 42,
    )
- Transpile these to Go struct literals.
- Positional arguments are ordered by inherited fields first (parent
  declaration order), followed by the class's own fields.
- Named arguments may initialize inherited fields; if multiple parents expose
  the same field name, qualify it with the parent name, such as `A.Name`.
- Constructor syntax should reduce repetitive Go initialization ceremony.
- The proposed pointer-returning constructor and instance `init` semantics are
  specified in `spec/constructors.md`. Until that proposal is implemented,
  this section describes the historical value-literal lowering.

String interpolation
- Support simple interpolation:
    "Hello {{this.Name}}, age {{this.Age}}"
- Expressions inside {{...}} are ordinary Go++ expressions.
- Initial transpilation may use fmt.Sprintf.
- The syntax should remain visually simple; avoid ${...}-style clutter.

Nil semantics
- Nil handling should be safer/easier than Go.
- A nil dereference should not automatically become a conventional exception model.
- Ordinary `.` access retains Go's ordinary nil behavior.
- Explicit safe member access uses `?.`:
    name := person?.Name
    greeting := person?.Speak()
- A safe access returns the member's zero value when its receiver is nil.
- When a safe access or safe-access chain is the left operand of `??`, a nil
  receiver selects the fallback instead of returning the zero value. A present
  member whose value is zero does not select the fallback:
    name := person?.Name ?? "Unknown"
- Within that coalescing form, safe field accesses may be chained from an
  identifier receiver:
    managerName := person?.Manager?.Name ?? "No manager"
- `??` does not recover panics from ordinary `.` access.
- Safe access starts from an identifier whose static type is a class pointer or
  generated class interface. Safe access is not inferred for ordinary `.`
  access or arbitrary receiver expressions.

Exceptions
- Exceptions are not a v0.2 priority.
- They are considered harder because Go has no native exception model suitable for transparent lowering.
- Prefer retaining Go-style explicit error handling unless a clean translation emerges.

Function defaults
- Function and method parameters may have trailing default values:
    func Greet(name string, punctuation string = "!") string
- Defaults are lowered at call sites; emitted Go declarations remain ordinary
  Go declarations.
- Calls may use named arguments, in any order:
    Greet(punctuation: "?", name: "Ada")
- Required parameters must precede default parameters. Named and positional
  arguments cannot be mixed.

Overloading
- Method/function overloading is desired as part of the broader Go++ ergonomics goal.
- Overloads with different parameter counts remain supported.
- Overloads with the same parameter count may differ by exact static parameter
  types, such as `Format(int)` and `Format(string)`.
- Calls with literals and statically known local values resolve by exact type;
  a derived class is assignable to a base class for polymorphic calls.
- Ambiguous or unknown call types remain ordinary Go++ errors to be tightened as
  type inference expands.

Polymorphism
- Base-typed variables should eventually dispatch to derived implementations:
    var p Person = Employee(...)
    p.Speak()  // Employee.Speak()
- This cannot rely only on Go embedding.
- Initial lowering supports local base-typed variable assignments and function
  parameters/returns by generating a method interface and storing pointers to
  concrete values.
- Polymorphic fields and cross-package base types use exported generated
  interfaces when their class has derived classes.
- Known concrete class-valued function and method results are lowered to
  pointers when they participate in inheritance, so they can flow directly
  into base-typed calls without taking the address of a non-addressable call.
- Compiler-generated dispatch/vtable structures are likely required.
- Preserve compatibility with emitted Go and Go stdlib types.
- The interface-based lowering covers class-typed variables, function and method
  parameters/results, fields, and direct derived-to-base call arguments when the
  static type is known.

Go interoperability
- Critical requirement: Go++ must use the Go stdlib without modification.
- Ordinary Go packages should be importable directly.
- Generated code should remain readable, debuggable Go where practical.
- Avoid requiring a custom runtime except for small helper support where absolutely necessary.
- Users should still be able to call normal Go functions/types naturally.

Concurrency/runtime
- Keep Go’s concurrency model unchanged.
- goroutines/channels remain Go’s goroutines/channels.
- Do not introduce async/await.
- Do not replace the Go scheduler/runtime.

Compiler architecture
- v0.2 remains a transpiler, not a standalone native compiler.
- Pipeline:
    .gpp
      -> lexer/parser
      -> AST
      -> semantic resolution
      -> Go emitter
      -> gofmt
      -> go build
- Start small and validate language ergonomics before building a sophisticated compiler.
- Ordinary Go syntax should pass through wherever possible.
- Compiler should parse only Go++ extensions initially rather than reimplement all of Go immediately.
- Semantic resolution builds package/class symbol tables before emission and
  rejects duplicate members, unresolved parents, and inheritance cycles.

Current v0.1 implementation scope (historical baseline)
- default package main
- optional package declaration
- flat source layout independent of Go package directories
- Go import declarations
- class declarations
- fields
- methods inside classes
- implicit this receiver
- inheritance syntax
- inheritance lowered initially through embedding, including nested compact
  construction of embedded parents
- multiple parent syntax
- ambiguous inherited member access requires qualification such as
  `this.Parent.Member`
- {{...}} string interpolation
- passthrough ordinary Go functions/code
- generated package directories
- generated Go formatting
- qualified cross-package compact construction for generated-module imports
- initial base-typed dispatch through generated method interfaces
- arity-based overloading for functions and class methods

Current v0.2 implementation scope
- named function and method arguments
- trailing default function and method parameters
- exact static-type overload resolution for same-arity functions and methods
- derived-to-base coercion for direct known call arguments
- known function and method result types for polymorphic call expressions
- explicit `?.` safe access for nullable class pointers/interfaces
- configurable CLI output directory
- anonymous structural records with deterministic generated Go structs; see
  `spec.records.md`
- compile-time-generated class descriptors through `obj.class` and
  `Class.fields`; see `spec.introspection.md`
- an implicit standard prelude for small slice, map, and string helpers; see
  `spec/prelude.md`
- extension methods on native Go and Go++ types; see `spec.extension-methods.md`
- lambda expressions with contextual parameter inference; see `spec/lambdas.md`

Explicit v0.1 boundaries (historical baseline)
- Go nil behavior is unchanged; safe member access is deferred.
- Exceptions are deferred; use explicit Go-style error returns.

Explicit v0.2 boundaries
- Exceptions remain deferred; use explicit Go-style error returns.
- Safe access initially accepts identifier receivers only.
- Overload resolution currently relies on exact static types and does not yet
  model conversions, interfaces, generic types, or arbitrary expression types.
- Expression result analysis currently covers known local functions and class
  methods; chained expressions and imported method sets remain future work.
- Generated dispatch remains interface-based rather than a hidden vtable runtime.

Near-term next features
1. Expand expression/type analysis for conversions, chained calls, and imported
   method sets.
2. Improve source-position diagnostics and add a first-class example/test runner.
3. Only later consider exceptions, generics, or other invasive runtime features.

Design principle
- Fix Go’s annoying surface-level warts while preserving the parts that make Go attractive:
  simple runtime model, synchronous-looking I/O, stdlib, compile speed, deployment, and low conceptual overhead.
- Do not add features merely because C++/Rust/C# have them.
- Every feature should justify its complexity and ideally compile away into straightforward Go.
